# 设计决策记录

> 每条决策以 `D<n>` 编号：**决策**、**备选与取舍**、**代价与重审条件**。新增或推翻决策时在此追加，不删除历史（被取代的标注"已取代"并指向新条目）。

## 一、仓库与形态

### D1. 独立仓库，经 PyPI 依赖 ChalkBase
**决策**：Agent 在独立仓库，通过 `pip install chalkbase` 使用知识库；开发期用 `pip install -e ../chalkbase` 联调。知识库不包含 Agent 代码，Agent 不读 `data/*.json`，只用公开接口。
**备选**：同仓库。放弃，因为二者生命周期、评测与发布节奏不同，混在一起会让知识库的收敛成果被 Agent 迭代干扰。
**代价**：跨仓库联调多一步；知识库接口变更需走版本号。重审：若 chalkbase 接口频繁变动。

### D2. 单仓库（backend / frontend / eval / docs）、单容器部署
**决策**：前后端同一仓库，FastAPI 同源托管前端构建产物，一个 Dockerfile。
**备选**：前后端分仓 / 分服务。放弃，因为个人项目的部署与联调成本不值得；同源还免去 CORS 与双域名。
**代价**：前端发布与后端发布绑定。

### D3. 技术栈
**决策**：后端 Python 3.11 + FastAPI + asyncio + Pydantic v2；前端 React + Vite + TypeScript；图用 d3 + dagre（与 ChalkBase 可视化一致）；公式 KaTeX。
**理由**：知识库是 Python；Pydantic 模型同时是领域模型与接口契约；React 生态完整。

### D4. 自研有类型的阶段管线，不用 LangChain / LangGraph
**决策**：`Stage`（带类型 IO 的异步函数）+ `StageRunner`（span、耗时、错误、可跳过、可重放）+ 一个有界工具循环（`AgentLoop`）。
**备选**：LangGraph。放弃的理由：①需要自有的事件 / trace 协议驱动 UI 与指标，框架的回调模型与之不匹配；②暂停 / 恢复 / 阶段重放需要对运行状态的完全控制；③依赖面与版本漂移风险。
**代价**：要自己维护约 500 行编排代码。重审：若需要分布式执行或长时间挂起的工作流。

## 二、Agent 行为

### D5. 默认创新：知识库是上下文，不是模板；用户意图优先
**决策**：默认 `novel` 来源（模型创作 + 核验），题型卡片作为"学生做过什么"的上下文；`template` 来源仅在用户明确要求基础 / 同类 / 批量题，或作核验对照时使用。Brief 字段带来源标记（`user > inferred > default`），先验只作用于后两者。
**理由**：产品价值在于创新与综合；程序化实例化的题虽然可验证，却等于"改教材原题"。
**代价**：`novel` 的答案正确性要靠分层核验保证（D9），成本更高。

### D9. 分层核验与诚实标注
**决策**：核验检查并行执行，汇总为 `verified / checked / needs_review / rejected`（见 architecture §4.4）；界面如实展示，`rejected` 不展示，先修复再重出。
**关键点**：求解程序与盲解**独立**（不同模型 / 不同提示 / 盲解看不到答案）；两路一致才标"已核验"。单路通过标"已校对"。
**备选**：只做一次自检。放弃，因为同一模型的自检会重复同样的错误。
**代价**：成本与延迟；用预算降级（F3）+ 缓存（E2）+ 并行缓解。

### D18. 澄清策略：假设优先，一次最多一问
**决策**：能默认就默认并亮出假设；只在缺失信息会大概率做错时提问，一次一个、带选项、允许"你来定"。
**理由**：教师时间紧，来回追问是最差的体验；假设可见且可一键改，代价低。

### D19. 长任务分阶段，运行可暂停恢复
**决策**：整卷任务按蓝图 → 样题 → 全卷 → 排版推进，每步可调整；运行有 `awaiting_user` 状态，阶段输出持久化。
**理由**：避免用户等很久得到不想要的结果；也是断线恢复与调试重放的基础。

### D20. 组合挖掘确定性优先，LLM 只做选择与创作
**决策**：知识点组合由 `ComboMiner`（图边类型、距离、教材题型的跨点共现、领域搭配）产生带理由的候选；LLM 选择并构想情境；候选不足时才用有界工具循环探索。
**备选**：全交给 LLM 通过工具探索。放弃，因为不可复现、慢、难以单独评测。
**代价**：打分函数需要用评测（A5c）调参，因此把权重放在配置里。

### D21. 受限执行：子进程 + AST 白名单 + 超时与内存上限
**决策**：模型生成的求解程序只在 `sandbox/` 里执行：独立子进程（`python -I`）、AST 白名单（仅 `Fraction` / `Decimal` / `math` 与少量内建，禁 import / open / dunder）、墙钟超时与内存上限。
**说明**：这是进程级隔离加源码过滤，不是操作系统级沙箱；容器本身是第二道隔离。输入端（用户文本、图片）不会被当作代码执行，只有模型输出的求解程序会被执行。

## 三、内容与导出

### D7. 题目内容统一为 Pandoc Markdown + TeX 数学；图形为结构化 `FigureSpec`
**决策**：见 architecture §4.3。
**备选**：自定义块 AST（段落 / 公式 / 图 / 表节点）。放弃：模型输出与人工编辑都是文本，AST 要额外互转，且更难 diff；Markdown+TeX 同时被 pandoc、KaTeX、各导出器原生支持。
**图形**：几何图与统计图必须精确，生图模型不能保证，因此由结构化规格渲染为 SVG（可验证、可编辑）；场景插图（生图）列为 P2。

### D8. 导出走 pandoc + Typst，不引入 TeX Live
**决策**：内容转换交给 pandoc（Markdown+TeX → docx（原生公式）/ latex / md / typst）；PDF 用 Typst 编译（单二进制，小镜像），版面模板自写；LaTeX 导出只生成源码，不编译。
**备选**：TeX Live（镜像数 GB，且编译用户内容有安全面）；无头 Chromium（内存与冷启动重）。
**状态**：S1 探针通过（2026-10-05）。实测：docx 中的公式是原生 OMML 对象（15/15）；LaTeX 源码保留 `rac` 等结构；Typst PDF 中文与公式渲染正确，预热后单页编译约 200～240ms（首次含字体加载约 2.3s）；pandoc 与 typst 均可通过 pip 安装（`pypandoc_binary`、`typst`），无需 TeX Live。
**发现的两个约束**（已纳入架构）：①行内公式的 `$…$` 内侧不能有空格（如 `$3.6-1.25 = $` 会被当作普通文本），而 LLM 常这样写——入库前需要**内容规范化**（修剪 `$` 内侧空格、把填空横线移出公式）并做 LaTeX 语法校验（D27）；②pandoc 的默认列表 / 选项排版不适合试卷（选项横排、题号悬挂缩进），**版面由自有 Typst 模板负责**，pandoc 只负责把单个题干转换成 Typst 片段。若后续发现 Typst 对某些版式不够用，退路是 Chromium 路线，`Exporter` 接口不变。

## 四、基础设施

### D6. 事件即真相
**决策**：运行产生 span 与事件，持久化为追加日志；用户进度条、调试台、指标、评测都读它（见 architecture §6）。
**理由**：避免"为调试再埋一套点"；回放与实时是同一份数据；指标不会评测与线上两套口径。
**代价**：事件量大，需留存策略（默认按会话保留期清理，调试快照另存）。

### D10. 角色别名 + 配置化模型；流式默认；缓存友好提示布局；录制回放
**决策**：见 architecture §7。主模型（qwen3.8 系列 / deepseek-v4.1-flash）**由角色级对比评测决定**，不预设；判官模型与被评对象不同源。
**实测事实（2026-10-05）**：新加坡 profile 可用；`usage.prompt_tokens_details.cached_tokens` 有返回，隐式缓存以 256 token 为单位、相同前缀第二次调用即命中；各候选模型接受图片输入。因此 KV 缓存命中率指标可直接测量。

### D11. SSE 而非 WebSocket
**决策**：服务端到客户端用 SSE（`Last-Event-ID` 续传），客户端到服务端用 REST。
**理由**：单向流足够；穿透代理与重连更简单；与事件日志的序号天然对齐。需在代理层关闭缓冲（`X-Accel-Buffering: no`）。

### D12. SQLite（WAL）起步，仓库接口隔离
**决策**：`store/` 以接口 + SQLite 实现；数据在 `VERICHALK_DATA_DIR`（云端挂卷）。
**备选**：直接 Postgres。放弃：本地零依赖更利于开发与评测；换库只需新增实现。暂不引入迁移工具，用 `schema_version` 表 + 启动检查；首次需要不兼容变更时再引入（遵循"不预先加组件"）。

### D13. 契约优先
**决策**：Pydantic 模型 → OpenAPI → TypeScript 类型（脚本生成，CI 检查无漂移）；事件 schema 带 `schema_version`。
**理由**：前后端字段不一致是全栈项目最常见的低级 bug。

### D16. 配置与密钥
**决策**：`pydantic-settings`；密钥只来自环境变量，绝不写入文件、日志、trace（日志脱敏 + 测试保证）；两个 DashScope profile（`cn` / `intl`）。

### D17. 匿名会话；调试台令牌
**决策**：无账号；浏览器持有随机会话 ID（请求头携带）；调试台生产环境需令牌。限流与配额本期不做（PRD §8）。

### D22. 试卷修改统一为 Patch + 快照
**决策**：见 architecture §4.3。撤销 / 重做 / diff / 版本回退共用一套机制。

### D23. 前端状态是事件流的纯函数
**决策**：用户端与调试台的运行状态都由事件 reducer 计算，实时与回放同一套代码。

## 五、评测与流程

### D14. 评测先行，三层评测，判官独立
**决策**：见 [evaluation.md](evaluation.md)。每个阶段先写评测规格与基线再实现；模型判官必须与被评对象不同源，且用标注数据校准；比例指标报告 Wilson 区间。

### D15. Badcase 闭环
**决策**：调试台 / 评测发现坏例子 → 归因（阶段、根因类别）→ 入 `eval/badcases/` → 在**对应层**修复（不在下游打补丁）→ 回归集防退化。修复必须能指明"哪个指标因此变好、哪些没变坏"。

### D24. 分层修复纪律
**决策**：问题发生在哪一层就在哪一层修（如超纲多源于特征抽取就修抽取，而不是在生成提示里加"不要超纲"）；一次修复若需要改动 3 个以上模块，先回到本文与架构文档评估是否缺少抽象。
**理由**：避免"小修小补"累积成面目全非。

### D25. 事件持久化：延迟合并提交
**决策**：事件追加走"延迟提交"（最多 50ms 合并一次提交）；同一连接内读写互相可见，任何非延迟写入会先提交挂起内容，因此回滚不会连带丢事件；关闭时统一提交。
**依据**：M1 基线显示逐事件提交时 10k 事件写入 3.23s（超出评测规格 3s 的门槛）；改后 2.4s，空管线一次运行 p95 6.0ms。热点是"线程切换 + 提交"。
**代价**：进程被强杀时最多丢失最后 50ms 的事件——此时该运行本来就会被标为中断（`mark_interrupted`），可接受。

### D26. 评测可复现要求检索也可复现
**决策**：chalkbase 的查询向量缓存目录指向评测录制目录（`eval/cassettes/chalkbase_embeddings`，随仓库提交）。回放时无需密钥与网络就得到相同的检索结果，从而提示词逐位相同、录制才能命中。
**说明**：chalkbase 的缓存是模块级全局，进程内首次加载后不随环境变量变化；生产里环境变量固定不受影响，测试里需显式重置（见 `tests/test_eval_smoke.py`）。

### D27. 题目内容规范化
**决策**：题目文本入库前经 `normalize`：修剪 `$…$` 内侧空格、把 `____` 与"( )"填空位置移出公式、统一全角 / 半角标点中的空白，并用 LaTeX 解析器校验数学语法，失败即走修复。
**理由**：S1 探针（D8）显示模型常见写法会让 pandoc 把公式当成普通文本，导致导出错乱；在内容进入 IR 的入口一次性解决，而不是在每个导出器里各自打补丁。

### D28. 消融实验是一等公民；首个案例：预热
**决策**：每个增加延迟、成本或复杂度的模块都注册为特性开关（`core/features.py`），可用 `--off` 关闭并由 `eval ablate` 输出对照表；模块进入主路径的同一里程碑内完成首轮消融，没有可度量收益就删除（evaluation.md §9）。

**案例：预热**。假设（来自产品负责人）：页面打开时先向模型发一遍提示词，把 KV 缓存写下来、把连接跑通，消除约 2 秒的"冷启动"。实验与结论（intl profile，本机网络；脚本 `scripts/ablate_warmup.py`、`scripts/probe_cache_ttl.py`，报告见 `eval/reports/ablation_warmup_*.md`）：

1. **检索的 ~2s 不是冷启动。** 拆解（新缓存、全新进程，各 3 次）：加载 Curriculum 约 0.65s（启动时一次性）；第一个新查询 2.0～3.0s，**第二个新查询仍是 1.5～2.9s**，缓存命中的同一查询仅 2ms；预热检索器后第一个新查询没有变快。时间花在**每个新查询的向量在线计算**。→ 预热检索器**无收益，已从预热中删除**。**后续更正（M2，D32）**：这 2s 的大头不是向量模型本身，而是 chalkbase 调用向量接口的方式——走本机 HTTP 代理、每次新建连接、并在锁内串行；改成连接池复用、直连后，查询向量约 0.3s。
2. **模型前缀预热有真实收益。** 每格 12 次、全新连接 + 随机盐前缀：~3k token 前缀 TTFT 中位数 1857→1445ms（−22%），~12k token 前缀 2435→1994ms（−18%）；命中缓存使输入成本分别降至 44% 和 23%。仅预热连接（不写缓存）的收益不可与噪声区分（n=5，约 −150ms）。
3. **代价**：预热请求本身要按未命中价付一次前缀费用；用户随后发起请求时，相对"冷启动"首次调用约多付 23%（12k 前缀），用户不继续则白付一次（约 ¥0.01 / 前缀）。收益只在"空闲后的第一次请求"出现；持续有流量时缓存自然是热的。

**结论**：保留 `warmup`，默认开启；有效期 `warmup_ttl_s = 240s`：缓存存活时间探针（`eval/reports/probe_cache_ttl_intl.md`）显示相同前缀在 300s 后仍命中、600s 后已失效，取 240s 留出余量。**重审条件**：M2/M3 的真实提示词定稿后重跑 `ablate_warmup.py`，收益与"关键路径上首次调用的阶段数"成正比；若首字延迟收益 < 200ms 或成本代价超过收益，则关闭。

## 六、意图理解（M2）

### D29. 路由并入理解，一次模型调用；其余全部由确定性代码完成
**决策**：原架构里的 `route` 与 `understand` 合并为一个阶段、**一次**模型调用（模型只做"读懂"：路由 + 扁平的字段 + 明说了哪些字段）；来源标记（user / inferred / default）、知识点映射、年级与学期推断、单元解析、目标课时、默认值与"本次假设"、**澄清判断**、上一轮范围的继承、展示用芯片，全部在 `understand_post.py` 里用代码完成。规则解析（`understand_rules.py`）与模型解析共用同一套后处理，既是评测基线，也是模型不可用 / 超预算时的降级（并告知用户）。
**理由**：①少一次调用省约 1.5s；②后处理可复现、可单测，两条路径共用；③澄清由代码决定，B2 就只取决于解析质量，且策略（"范围缺失 / 范围冲突才问，一次一问"）与提示词解耦。
**澄清规则**：范围缺失（无年级、无知识点、无单元，且不能从上一轮继承）→ 问年级（6 个年级各一个选项）；范围冲突（用户明说的年级，比该主题在知识库里最早出现的年级低 ≥2 年）→ 问"按哪个年级出 / 保留年级换内容"。回答后重新理解一次，不再追问。
**代价**：模型输出的字段名较多，提示词较长（约 4k token，缓存命中率 0.95，成本约 ¥0.0006 / 次）。

### D30. `fast` 角色选 deepseek-v4.1-flash
**决策**：在意图理解任务上对比 qwen3.8-flash、qwen3.7-flash、deepseek-v4.1-flash（val，作者集 + 换说法集），质量在置信区间内无差别，deepseek-v4.1-flash 最快（理解阶段 p50 约 1.6s 对 2.15s），选它。数据见 [eval/specs/understand.md §5.2](../eval/specs/understand.md)。**重审**：M3 之后 `fast` 还要承担编辑、回复等任务，届时重新对比；换说法集由 deepseek 改写，对它可能有轻微偏向（作者集上三者持平）。

### D31. 理解各模块的消融结论
上下文（保留，关掉后 B2 精确率 1.0→0.70、B3 0.974→0.923）、示例段（保留但**证据混合**：换说法集上来源准确率三次重复一致 +0.03～0.055，作者集无差异，字段通过率略降，成本 +24% ≈ ¥0.0001）、检索并行（保留，冷缓存下快 370ms）、模型本身 vs 规则（保留，规则做降级）、主题重检索（保留但证据偏弱）。**方法教训**：温度 0.3 下单次对比的噪声约 ±0.01，结论必须重复验证——示例段的收益在第一次测量里被高估了。详见 [eval/specs/understand.md §5.3](../eval/specs/understand.md)。

### D32. 查询向量：连接池 + 直连 + 锁外请求（修在 chalkbase 一层）
**问题**：chalkbase 的 `embed()` 用标准库 `urllib` 发同步请求：走环境代理、每次新建连接（TLS 握手）、并且在全局锁内进行，导致并发查询被串行化。本机实测一个新查询的向量请求：现状中位数 **4.8s**（1.6～9.4s）→ 直连但每次新建连接 1.4s → 直连并复用连接 **0.64s**（最快 0.25s）。
**决策**：在 chalkbase 增加 `query.embed.set_embedder(fn)` 注入点，并把网络请求移到锁外（锁只保护缓存读写）；verichalk 的 `knowledge/embedding.py` 提供基于 `httpx.AsyncClient` 的实现（连接池、不走代理、可并发、失败时让 chalkbase 降级为词法检索），预热时顺带建立到向量接口的连接。注入点向后兼容：没有它的旧版 chalkbase 沿用自带实现。
**状态**：chalkbase 0.1.1 已发布到 PyPI（含该注入点），verichalk 依赖 `>=0.1.1,<0.2`；生产镜像从 PyPI 安装，向量请求走连接池复用的快路径。

## 七、规划与创作（M3）

### D33. 组合挖掘：确定性、有"桥"、只用适合文字出题的知识点
**决策**：综合题的知识点搭配由 `ComboMiner`（`knowledge/graph.py`）在知识图快照上产生：信号为直接关系边、教材共现、教学位置接近、同主线、共同邻居、共同情境（权重在 `config/plan.yaml`）。跨主题搭配**必须有一条"桥"**（直接边 / 教材共现 / 共同邻居不低于阈值），只靠"教学位置相近 + 都出现在购物情境"会拼出"小数加减 × 平移与平行"这类牵强组合；搭档只取教材里有不依赖图形题型的知识点。规划模型只在候选里**选择与构想情境**，确定性约束（题量、档位分布、范围合法、情境不过度重复）全由代码保证，模型不可用时降级为确定性蓝图。
**评测的诚实记录**（`eval/specs/plan.md`）：教材里真实的跨点搭配 96% 在同一领域、70% 在同一单元，因此"留出召回"主要奖励教学位置接近——"教学位置最近邻"基线已有 0.751@10，组合挖掘 0.772~0.85@10（取决于权重），随机 0.132。这个指标只能当"不退步"的底线；"创新搭配是否自然"由综合题真综合率（A5c）与判官评测衡量。
**代价与重审**：打分权重按留出召回调到了偏重教学位置（proximity=1.0, edge=0.6），有过拟合教材习惯的风险，需在首批 P5（判官自然度）数据后复核。

### D34. 创作：先算后写，答案结构化，可核验的答案形式
**依据**：实现前对通用大模型的探测显示，27 道题里 4 道的答案字段与自己的解析矛盾（模型在写答案时还没算完，解析里才"等等，重新算"）。多模型对比（12 个请求，每个配置 44~57 道，两个不同厂商的思考模型审计）：直接出题的答案错误率 qwen3.8-max 5.3%、qwen3.8-max 思考 8.8%、qwen3.7-plus 0%、qwen3.8-flash 13.6%、deepseek-v4.1-flash 5.7%、deepseek-v4.1-flash 思考 0%——**各模型都会错，思考模式不稳定地改善**。
**决策**：①JSON 字段顺序固定为 草稿 → 求解程序 → 题面 → 选项 → 结构化答案 → 解析；②显示的答案由结构化答案拼装，求解程序必须返回与之同序的精确值；③答案只能是数值 / 选项字母 / 对错（"列出算式""写出方程"类答案没有标准形式，无法独立核验）；④选择题的程序返回**正确选项的内容**，字母由检查映射（让程序生成字母会触碰沙箱白名单并反复失败）；⑤规范化入口（D27）修复 JSON 里 TeX 反斜杠被当作转义的问题。
**代价**：写题输出变长；草稿区限制在 150 字。

### D35. 核验：便宜的检查在前、模型检查并行；盲解与抽取用非思考模型
**决策**：`verify_item` 先跑结构与求解程序（确定性），失败即进入修复，不花模型调用；通过后盲解、边界抽取、题面质量并行。`solver`（盲解）与 `extract`（超纲特征抽取）选 deepseek-v4.1-flash **非思考**：核验评测集上思考与非思考的检出率相同（错答检出 0.933；超纲检出 0.96~1.0），非思考快 1.7~4 倍、便宜约一半。
**评测集的局限（已知）**：VerifyBank 的错误主要是程序化注入（数位滑错、±1、小数点移位、运算选错），三个候选模型在其上都到天花板，**区分不了盲解模型**；真正的区分要看端到端里写题模型自己犯的自然错误（审计判错）。BoundaryBank 的模板来源 `in` 标签只依据参数的数值特征，比"整题含运算结果与单位"的抽取更宽松，所以范围内"误杀"数里有一部分是标签偏宽（如 77+51 的和 128 超出一年级 100 的数域），按来源分开报告。
**重审条件**：若端到端审计显示"已核验却错"的题集中在某类，则在核验层补该类检查。

### D36. 延迟与成本预算
**问题**：首次端到端 3 道题 279 秒、¥1.06。**拆解**：边界抽取思考模式平均 22 秒（占大头）、每道题平均写 2.4 次（选择题的求解程序反复触碰沙箱白名单；"哪个说法正确"式选择题不可程序验证；答案漏问）。
**决策**：①抽取改非思考（22s→2.5s）；②修复最多 1 次，其后从头重写 1 次；③单题时间预算 45 秒，超过后不再开始新尝试（有界延迟）；④写题模型 `smart` 选 qwen3.7-plus：与 qwen3.8-max 的交付数和一次通过率无差别（74/79 对 46/51），价格约 1/6（单题成本 ¥0.053 → ¥0.018）；kimi-k3 试过，一次通过 19/28，不优于 qwen3.7-plus；⑤丢弃的题换"更稳妥的规格"补一轮（单知识点、数值答案），以达到教师要求的题量。
**评测纪律**：迭代用 `scripts/probe_produce.py`（只跑创作阶段、不审计、多请求并行，一分钟内出结果），完整评测（含审计）只在里程碑验收时整套跑；审计并发调到 20。

### D37. 审计独立于线上核验
**决策**：端到端评测里 A2 / A3 / A6 不用线上核验自己的结论打分：答案正确由两个不同厂商的思考模型独立解题（一致才定论，分歧列为"争议"单列）；不超纲由 chalkbase 自带的特征抽取（不同模型、不同提示）+ `check_item`；题面质量用同一份评审标准、更强的评审模型。审计结果缓存在 `eval/audits/`（随仓库提交），配置变化（模型 / 版本）使缓存失效。
**局限**：审计与线上核验都依赖语言模型，是"独立"但不是"人工真值"；争议项需人工复核。

### D38. `template` 来源：答案可靠，题面质量不保证
**发现**：教材题型实例化的答案由知识库程序算出，但题面常有缺陷（括号里写两种情境、人物价格荒谬如"书包 967 元比文具盒便宜 4/5"、判断题标签下答案是数值）。
**决策**：`template` 路径仍过结构与题面质量检查；每个知识点备选 3~4 个题型，质量不过就换种子、换题型，并在本次运行里记住已知有缺陷的题型；规划只选有程序化题型（不依赖图形）的知识点。效果：三个课本式请求的交付从几乎全军覆没提升到 30/32。**上游反馈（根因 K）**：这些题型的题面缺陷应在 chalkbase 修复，已记入待办。

### D39. 删除新颖度检查（消融的第一个结论）
**证据**：①base1（156 道交付题）里与教材示例雷同 0 道，首次被拦的检查里新颖度只占 1/183；②套内重复仍有 14%（朴素基线 41%），说明它没挡住真正的重复，套内多样性实际来自规划（考法结构、情境各不相同）；③40 道原始初稿的逐层贡献实验里，其余检查合起来只漏 3/18 的真问题，新颖度不在其中。**决策**：移除 `check_novelty`、`produce.novelty_check` 开关及其输入（教材示例 / 上传题 / 套内题面的比较语料）；相似度函数保留给评测的 A5 指标。**重审条件**：接入用户上传的题（M4）时，"不得与上传题雷同"是产品承诺，届时在对应位置重新引入并附消融。
**同一实验的其他读数**（n=40 初稿，真值来自独立审计）：初稿里超纲 11/40（27%）、题面质量差 5/40、答案错 2/40；超纲检查有 3 道独有抓取，盲解 1 道，题面质量 2 道，求解程序与结构检查 0 道（二者各有不属于审计真值的合法拦截，如格式与程序自洽）。求解程序 vs 盲解是否冗余待更大样本（目标 150 道初稿）。

### D40. 三种"提升题目质量"的策略探索：都没有采用，杠杆在上游
**背景**：产品负责人指出，只满足答案正确与不超纲的评测会把题目做成"正确但平庸"；教师真正缺的是**跨单元、整学期的综合题**（练习册按单元配题，期末区统考考整学期综合，学生不会应对）。为此在同一批 10 个请求（`eval/datasets/quality_probe.yaml`）上，由三个相互隔离的子任务各探索一种策略，用同一个盲评（`scripts/compare_sets.py`：交换顺序评两次、一致才算胜负，评审与写题模型不同厂商）对比。
| 策略 | 做法 | 结果 | 结论 |
|---|---|---|---|
| S1 候选择优 | 每个题位写 3 个候选，由另一个模型挑一个再核验 | 对照下 4/3/3、3/3/4（胜/平/负），无效应；成本约翻倍 | **不采用**：规划已经定死了情境、考法和靶子，三个候选近乎相同，挑选无对象；挑选模型偏好更长更复杂的题面 |
| S3 评审改稿 | 通过核验后由评审模型打分并要求改写一次 | 同稿配对 2/7/0，对基线 4/2/0（但交付数 23 对 13，主要是交付差）；7 个被接受的改写里 1 个有实质提升，2 个把知识点改丢而核验拦不住；成本约 +50% | **不采用**：多为装饰性改写，且有"知识点漂移"风险；若重做，评审必须对改写前后做 A/B 并检查知识点保留 |
| S2 范例驱动 | 33 道手写区统考风格范例按考法 × 年级注入规划与写题提示词 | 4/3/2，但交付 16 对 24，写题慢约 12% | **证据不足，暂不合入**；范例库保留为资产（`eval/annotation/exemplars/design_exemplars.yaml`），将来重测时只对难度 ≥ 3 且非"直接应用"的题注入 1 条 |
**共同发现**：①真正的杠杆在**上游**（规划让情境与考法本身多样、意图不丢），而不是写完后再挑或改；②探索集本身偏难（多主题、综合、区统考风格），在足够并发下创作阶段只交付 22/40，一次通过 11/40——**交付率才是当前最大的短板**；③探索过程中暴露并已修复三个缺陷：题面出现字面 `\n`；用户明说年级时，映射和目标课时被检索命中的高年级知识点盖过（"三年级的周长"被映射到六年级的圆周长）；多主题请求（"乘法和周长"）的综合题没有在用户点名的主题之间组合；④评测纪律：多个探索并行时，共享的 `llm_concurrency=8` 会让题目排队、被 45 秒预算截断，所有对照必须在同一并发条件下进行。
**先验的处理**（产品负责人强调）：整学期综合是**默认倾向而非硬性模式**：范围是整学期 / 整年级、没点名知识点也没限定单元时，综合题默认选同一学期、不同单元、不同主题且有桥的搭配；用户限定了单元或知识点，搭档不跨出所限范围；明说"复习"时才放开到更早的内容。

### D41. 两条链路一键切换：`classic`（默认）与 `design`
**问题**：为"好题"做的改动让端到端交付从 0.90 降到 0.654（见 D40 与 roadmap），但它们也确实让综合题更有设计感（跨主题、跨单元、针对易错点）。既不能丢掉这些探索，也不能让回退进入默认路径。
**决策**：把这些改动收成四个**选择性开启**的开关（`Feature.default=False`）：`plan.design`（规划提示词 v2：考法结构与易错点，读取知识点详情）、`produce.design_prompt`（写题提示词的"什么是好题"、考法结构、难度的结构要求）、`produce.difficulty_check`（判官估计难度低于要求 2 级以上判不合格）、`plan.cross_unit`（整学期综合的跨单元先验）。预设 `pipeline`：`classic`（**默认**，M3 中期 mid1 验证过的行为，加上与"好题"无关的缺陷修复）与 `design`（四个开关全开）。切换方式：环境变量 `VERICHALK_PIPELINE=design`，或评测 / 探针的 `--pipeline design`；单项用 `--on 名称` 开启、`--off 名称` 关闭（`off` 优先，例如 `--pipeline design --off plan.cross_unit` 就是二分实验）。
**classic 不等于逐字节的 mid1**：始终保留的修复有——用户明说年级时不被检索命中的高年级知识点盖过、多主题请求在用户点名的主题之间组合、算式 / 方程答案按值或解比较、中文数字归一、字面 `
` 还原、沙箱允许 `prec`、模板题具体解析与主知识点匹配、删除新颖度检查。
**重审条件**：二分找出回退的原因后，把不伤交付的开关并入默认，把代价大的收窄或删除，最终不留两条长期并行的链路。

### D42. 导出：片段化转换 + 自有版面 + "预览即导出"
**决策**：①`PaperView`（`render/view.py`）把 `Paper + ExportOptions` 变成与格式无关的排法（题号、分区编号、分值、学生 / 教师版、答案位置），四种格式共用，只在这里决定也只在这里测；②全卷文本用占位符拼成一份文档、一次 pandoc 调用转换再拆回（每次导出一个子进程），填空线与插图引用在转换前换成占位符；③PDF 由自有 Typst 模板排版（含分数的行内公式用显示样式），Word 用修补过的 reference.docx（宋体 + Times、数学区字体、正体数字、无边框选项表），Markdown 自包含（SVG data URI），LaTeX 只生成源码（有图时 zip）；④**没有单独的分页预览**：前端"试卷视图"直接嵌入 PDF 导出（`inline=true`），预览与导出同源，保真问题只有一处要查；⑤图形：`FigureSpec → SVG` 纯函数（数轴、条形统计图、几何图形、方格 / 坐标图），Word 与 LaTeX 用 Typst 栅格化为 PNG，画不出来的图降级为题内占位并给警告，不阻断导出；⑥导出前检查字符字形（Typst 缺字不报错只画方框），缺字与缺中文字体都作为警告返回。
**证据与教训**：第一版评测集全绿（120/120）而页面上有分数过小、选项重叠、Word 数字斜体等问题——自动检测只能保证"没丢、没泄、没崩"，版面保真必须人工看页面（X4）。
**未做**：首批图形类型是按常见题型判断的（知识库里的 `figure_types` 是自由文本，无法统计）；写题阶段还不产出 `FigureSpec`（属 M3 后续），所以带图的题目目前只能由编辑或测试数据提供。

### D43. 修订是线性、只增不删的历史；撤销 / 重做 / 复核都是新增修订
**问题**：手改、撤销、重做、回退、后台复核（只更新核验状态）要共存，而且后台复核不能让用户"撤销"撤到一条看不见的修订，也不能覆盖用户刚改的内容。
**决策**：`revisions` 线性追加；每条修订带 `kind`（edit / undo / redo / restore / review）与**逻辑版本** `logical`：edit / restore 的逻辑版本是它自己，undo / redo 是被恢复的那个版本，review 与它所复核的版本相同，因此对撤销栈**透明**；edit 记 `parent`（它基于的逻辑版本），撤销沿 `parent` 往回走；重做栈存在修订上，任何新的 edit 清空它。一个逻辑版本的"最新内容"取该逻辑版本上最后一条修订（含复核结果）。复核结果只在该题 `rev` 没变时落盘，用户在复核期间又改了就作废（R2）；客户端的 `base_rev` 只在**内容**修改（非复核）发生过时才算冲突。diff 由两个快照计算（纯函数）。
**手改的约定**（`apply_user_edit`）：内容字段被改的题核验状态回到 `pending`、来源标为 `edited`、过期的结构化答案丢弃；同一补丁里显式给出核验结论的（智能体改写）以它为准。手改题没有求解程序，复核最多"已校对"，不合格标"需复核"而不是丢弃（教师自己的题不能凭空消失）。
**证据**：随机操作序列与参考模型对拍的属性测试；复核评测里错误编辑检出 10/10，关闭复核则 0/10。

### D44. 自然语言编辑 = 模型译成编辑计划 + 确定性执行；改写复用创作阶段
**决策**：模型（`fast`）只把一句话译成**小词表里的计划**（改写 / 只改文字 / 删除 / 移动 / 交换 / 设分值 / 设总分 / 改标题）；整句都是确定性动作时直接走规则不调用模型。教师点名的题是**硬范围**（理解阶段给出目标，计划里超出范围的题号被丢弃），未点名的题不进入执行——"附带破坏"在结构上被排除；所有改动合成一个补丁、一条修订，一次撤销回到改前。**改写**不另写一条模型路径，而是把原题与教师要求作为上下文交给创作阶段（写题 → 程序 / 盲解 / 边界 / 质量核验 → 修复），因此"复核通过"免费获得；改写失败的题保持原样并告知，其他题照常。
**附带决定**：①多知识点的题改写后仍要同时用到它们（按综合档处理）；②复核只得到"需复核"时整体再试一次；③**选择题答案字母由求解程序的结果推出**（`fix_choice_letter`）：模型常把正确值写进选项却把字母指向别处，字母本来是派生信息，由程序推出比让模型对齐更可靠，之后的盲解仍会独立核验；④难度改写在提示里写明"原题难度→目标难度"与具体办法。
**证据**：见 eval/specs/edit.md §5（C1 0.897 / 留出集 17/17；② 恒为 1.000）。

### D45. 整卷：确定性细目表 + 两个检查点；追加是默认，替换要明说
**决策**：①细目表（分区 × 题型 × 题量 × 分值 × 难度梯度）由规则从 `Brief.paper` 生成：题量按时长估计（约每 5 分钟 2 道），题型默认比例或教师指定的结构，分值按题型权重分配、**合计恰好等于总分**（最大余数法，尾差补在权重高的题型），难度整卷从易到难；②规划阶段按题位出题（题型与难度由题位决定，综合题锚点优先取单点题没覆盖到的知识点）；③`blueprint` 检查点（确认 / 一句话调整，调整由模型译成结构化调整项再由规则重排，最多两轮）→ 样题（不同题型各一道，上屏并在 `samples` 检查点确认 / 重出一次）→ 全卷并行创作与核验 → 按细目表装配（有题被丢弃时按权重重新分配，总分不变）。不支持检查点的环境（评测）或关闭 `paper.staged` 时一次出完。④出题请求遇到已有试卷默认**追加**到最后一个分区（教师不会因为说"再来 3 道"而丢掉已有的东西）；明说"重出 / 换一批 / 全部换"才**替换**（一条修订，可撤销）；整卷请求替换已有试卷。
**教训**：整卷蓝图评测的第一次运行就暴露了规划里的一个潜伏缺陷（窄单元里综合题降级时多取单点知识点，`StopIteration`）——确定性评测对"结构性"缺陷很有效。

### D46. 追问只读，上下文是被问到的题；`answer.context` 的收益目前不可度量
**决策**：追问（场景 S7）只读：题号由规则从问题里解析（"第 3 题""第三题""第 1、2、3 题""最后一题"），被问到的题（至多 3 道）连同知识点说明与常见错误进上下文，其余题给概览；回答以题目已核验的答案与解析为准，认为题目有问题要直接指出而不是悄悄改答案；指代不清请教师指明题号。
**诚实记录**：`answer.context` 消融在 20 例上 20/20 对 20/20，判官区分不出；保留是出于"回答可引用知识库而不是编造"的定性理由，不是度量结果。**重审条件**：补一个"是否引用知识库内容"的判官后重测，无收益则删除。

## 八、前端（U1 / D1）

### D47. 一个应用、三个分区；运行状态是事件的函数；会话控制器与界面分离
**决策**：Vite + React + TypeScript（strict）单应用，`/` 用户端、`/debug` 调试台（按需加载，普通用户不下载它的代码），共享 `shared/`（接口客户端、事件 reducer、公式渲染、设计令牌与基础组件）；ESLint 规则禁止 `user/` 与 `debug/` 互相导入。**类型不手写**：`scripts/gen_types.py` 由后端 OpenAPI 生成 `schema.gen.ts`（`--check` 检查漂移），`types.ts` 只做命名并把"响应一定带全字段"的类型还原（`Full<T>`）。
**状态**：一次运行的状态由 `reduceEvent`（纯函数，按 seq 去重）从事件日志推出，实时订阅、断线续传、调试台回放用同一份代码（D23）；**试卷内容由服务端持有**——`paper.patch` / `item.status` 只告诉界面"试卷变了"，界面据此去取最新试卷，不在前端重新实现补丁（避免两套补丁语义漂移）。跨组件的流程（发送、订阅运行与手改后的复核运行、检查点、撤销 / 重做 / 回退、断线后恢复会话）放在**不依赖 React 的 `SessionController`** 里，用 `useSyncExternalStore` 接到界面——这样可以用 mock 的接口与事件流单元测试，而不是只能靠浏览器测。
**公式**：题目文本（Pandoc Markdown + TeX）由 `shared/math/parse.ts` 解析成小语法树（行内 / 独立公式、填空线、插图、竖线表格、列表），按 Pandoc 的规则判定 `$…$`（结尾 `$` 后不能紧跟数字，避免把"$5 和 $6"当公式），KaTeX 渲染；单个换行视为空格、空行分段，与导出一致。
**界面原则的落地**：①说老师的话（`labels.ts` 是内部标识到教师语言的唯一映射，未知的核验项统一叫"其他检查"，知识点 ID 永不显示——取不到名称就不显示）；②任何点击 ≤ 1s 有可见反馈（发送后先本地显示"已收到，正在开始"，再等网络）；③进度卡显示当前步骤、已用时间（每秒更新，让教师知道没卡住）和"停止"；④每个异步操作有进行中 / 完成 / 失败三态，失败说明原因与下一步；⑤手机宽度下对话与试卷用底部标签切换。

### D48. 逐题上屏：新增 `item.delivered` 事件（schema 1.2），不为此制造中间修订
**问题**：PRD 原则 2 要求"第一道题通过核验就先展示"，但后端要等全部题完成才装配成一条修订（`paper.patch`），逐题上屏其实没有实现——用户端会先空等整个运行（实测 30～225 秒）。
**决策**：每道题通过核验后发一个用户可见事件 `item.delivered`（带完整的 `Item` 与送达序号），用户端把它们显示为"草稿"卡片（虚线框、不可编辑），整份试卷装配完成的 `paper.patch` 到达后以真正的试卷替换。**不**在运行中途逐题写修订：那会让撤销栈 / 版本历史里出现半成品，破坏 D43 的线性历史与"一次出题 = 一个版本"。**代价**：送达的题与最终装配的题可能不同（装配时排序、分值、丢弃补题），所以草稿只是预览，界面不让教师在草稿上操作。

### D49. 试卷视图用 pdf.js 绘制导出的 PDF；不用浏览器内置查看器，也不另做近似排版
**问题**：D42 定了"预览即导出"（试卷视图嵌入导出的 PDF）。第一版用 `<iframe>` 嵌 PDF，在 Edge 里缩放不受 `#view=FitH` 控制（页面比框宽、被截断），移动端浏览器通常根本不在页面里显示 PDF。
**决策**：前端用 pdf.js（只在打开"试卷"视图时才动态加载）把 PDF 逐页画到 canvas，宽度跟随容器，一次绘制失败只降级为"预览暂时生成不了，不影响导出"。**备选与放弃**：另做一套 HTML 分页预览——两套排版会各自出错，违背 D42 的"保真只有一处要查"。
**代价**：多约 440 kB（gzip 131 kB）的懒加载脚本与 1.2 MB 的 worker，只在用到时下载。

### D50. 调试台：自绘 span 树、学期分层图与调用检查器；Badcase 入库是 YAML 文件
**决策**：数据全部来自事件日志（`/api/debug/runs/{id}/events` 与实时的 `.../stream`，事件按 seq 去重后与回放同一份 `buildModel`）。①**流程与时间线**合为一个视图：左 span 树（阶段 → 工具 / 模型 / 检查，默认只展开到阶段，逐题并行的子流程点开才看），右同行瀑布条，并行的逐题子流程在时间轴上并排；②**图检索视图**按学期分层（列 = 学期，从早到晚）自绘 SVG，不用 dagre——自动分层会打乱"学期"这个本来就有的排布；命中节点按角色着色，选中的组合高亮，边按类型区分，滑块逐步回放检索过程，点击节点取知识点说明（`/api/debug/kp/{id}`）；③**调用检查器**显示提示的分段（静态 → 稳定 → 动态）与缓存命中位置、完整消息、输出与参数；④**题目证据**列出每道题全部核验项及其证据（程序输出、盲解过程、边界特征与违规）；⑤**Badcase**：一键入库，必填根因类别（决定修在哪一层），记录是 `eval/badcases/*.yaml`（开发态）或数据目录（部署态），一条一个文件，可读可 diff 可直接提交。
**未做**：从指定阶段重放（需要运行状态快照的恢复接口，放到有真实需求时）；两次运行的差异对比（现在能并排开两个标签页）。

## 九、感知（M4）

### D51. 照片识别：视觉模型只做"读"，其余都是确定性代码；画质差由代码要求核对
**决策**：`perceive` 对每张图一次视觉模型调用（多张并行；一张失败只把那张标成不可用），输出**分组 JSON**（大题 = 题号 + 共同题干 + 若干小题，一排 36 个口算只需约 1500 token）；确定性后处理负责扁平化、把"看不清"标到具体小题、按页面标题与各题知识主题**并行检索知识点**（取得分不低于最高分 60% 的前 3 个）、汇总学生上下文（学段取题数加权的众数，只留学段内的知识点，课时取其中最晚的）。提示词（`perceive.read` v2）的关键约定都来自首轮失败：①只转写要学生作答的题，"算法整理"示范区、页眉页脚、二维码、手写、**纸张背面透印**、相邻页露出的半页一律不算；②连线 / 分类 / 读图题整题一个小题，共享一张图的小问合并；③图中的对话气泡与图上数据属于题面；④输出前从页面底部往上自查（flash 模型会漏掉页面下半的带图题）。
**预处理**（`perception/`）：按 EXIF 转正、长边限 1600px、统一 JPEG，不做自动裁切与透视校正——真实照片的倾斜、透视、反光、遮挡、缩到 640px 的低清照片上视觉模型都读得对（见 perceive.md §5），不为没有观察到的失败预先加组件。**只在极端情况下确定性拒绝**（几乎全黑 / 全白 / 过小），其余画质问题只给拍摄建议。
**模型选型**（`vision` 角色，15 张真实页、190 题）：qwen3.8-flash 题级一致 0.955、数字错误 ≈ 0、p50 约 6s、单张 ¥0.0025；qwen3.8-omni-flash 0.955（精确率更高、字符错误率略高）；qwen3-vl-plus 0.920；qwen3-vl-flash 0.884（常把一道题拆碎、精确率 0.77）。flash 与 omni 在这个样本量上分不出高下；**选 flash**——价格已知且最低，且按独立性规则 omni 是标注交叉核对用的模型，不能同时是被评对象。重审条件：用户新拍的验收页上两者再比一次。
**消融**（perceive.md §5.4）：关掉 `perceive.topic_search`（只按页面标题检索）B5 top-3 从 0.948 掉到 0.370——每日一练的页面标题与题目内容常不一致，必须逐题检索；预处理（转正 + 1600px）对 B4 无可度量影响但省约 20% 成本；长边 1024 的数字错误率（0.015）已贴近阈值，取 1600。

### D52. 照片是"学生上下文"和"防雷同集合"；用户明说的永远优先
**决策**：照片给出的范围与习惯进入 Brief 时来源一律标 `inferred`：年级 / 学期 / 知识点 / 目标课时只在**用户一句话没有指明范围**时采用（采用后不再追问年级）；难度与题型在用户没说时参照照片（题型只在照片里不超过两种时才推断）；用户明说的（"五年级的""选择题"）永远覆盖。照片里的题作为**参考题**进入两处：①写题提示的"学生做过的类似题"（均匀取样 3 道，借考法与难度，数字与情境要换）；②确定性的**防雷同检查** `novelty`（核验链路里与 `structure` 同级的便宜检查，失败走已有的修复 / 重写）。
**翻版的定义**：同类算式换了数字**不是**翻版（"照这页再出 5 道"本来就要同类题）。`copy_score` 以字面三元组的 Jaccard 为主，数字序列完全相同（≥ 2 个数）时再按"形状"比一次；≥ 0.75 判翻版。**为什么不直接用 M3 的 `similarity`**：它把数字抹成 `#`，同形算式一律 1.0，会把所有同类题都拦下。
**代价与边界**：只有被教师确认的（或没有看不清标记的）题进入防雷同集合；`template` 来源的题不过这个检查（题型实例化的数字来自知识库种子，雷同概率极低，且尚未观察到失败）。

### D53. 看不清：模型的自我报告不可靠，用确定性画质判断兜底；低置信 / 画质差就暂停让教师核对
**观察**：把照片压到 640px、强压缩后，模型把 1.98000 读成 1.96000、把 ÷ 读成 +，**一处都没有标成不确定**（P7 召回 0/2）；它标出来的"看不清"在清晰照片上几乎不出现。
**决策**：①模型自报的 `doubts` 照用（有标记的小题必须核对）；②**确定性画质判断**（清晰度 = 边缘滤波响应的方差，在固定 800px 缩略图上算；亮度、对比度、短边）：阈值按变体集标定，真实清晰照片的清晰度 ≥ 1480，模糊 / 压缩变体 ≤ 860，画质差（`poor`）的照片整页都要核对；过亮只提示不强制（白底清晰页很常见）；③有任何需要核对的内容就触发 `perception` 检查点：只展示需要核对的题（其余可展开），教师可改字、去掉某题、直接确认；全部高置信且画质正常时**不打断**，识别卡片留在对话里（可展开）。结果：模糊 / 过暗 / 低清变体 13/13 被要求核对，真实清晰照片 0/15 误报。
**诚实记录**：P7 的"模型自报召回"样本太少（n=2）无法下结论，已由确定性画质判断兜底；兜底只能覆盖"画质差"导致的读错，不覆盖清晰照片上的个别笔画误读（本批 190 题里数字序列读错 0～1 处）。

### D54. 图片的隐私与可观测性：只在请求里，记录里是占位
**决策**：图片以 data URI 只出现在发往模型的请求里；`llm.call` 事件与调用记录里的图片替换为"大小 + 哈希"占位（调试台仍能看到分段与提示文字，看不到图片字节）；录制的键是请求哈希，录制文件不含图片。上传文件落在数据目录（不入库、不进事件），`GET /api/sessions/{id}/attachments/{att}` 只能取本会话的附件（其他会话 404），默认返回 720px 缩略图。事件 schema 升到 1.3（`perception.ready`、检查点种类 `perception`）。
**评测数据的版权**：真实练习册照片、标注、识别报告、识别录制都含教辅题面，一律不入库（`.gitignore`）；端到端测试用程序合成的练习页（`frontend/e2e/fixtures/`，无版权）。

### D55. 界面换成靛蓝浅色主题；颜色只在令牌里
**决策**：原"纸色暖灰 + 黑板绿"换成冷白底（带一点淡蓝与暖桃的光晕）+ 靛蓝品牌色 + 粉笔琥珀点缀（只用于标签与重点标注，不做大面积底色）；欢迎页底纹是淡到几乎看不见的方格纸，标题里"出什么题"用荧光笔式的琥珀下划线；用户气泡用品牌渐变，输入框的发送键同色。颜色仍只在 `shared/ui/base.css` 的令牌里定义（调试台共用，其硬编码的类别色同步换成品牌色）；所有前景 / 背景组合保持 ≥ 4.5:1（axe 的 serious / critical 为 0，端到端检查）。

### D56. 调试台接一个分析助手：摘要常驻、细节按需查；历史对话可改名与删除
**问题**：一次运行有上百个事件与十几次模型调用，开发者逐条翻记录才能回答"这次为什么慢 / 为什么这题被拦"。**决策**：调试台的运行详情里加一个"AI 分析"视图，围绕**这一次运行**多轮对话。上下文分两层组织（`orchestrator/run_digest.py`）：①**摘要**（约 5k～30k 字，有预算，超出时先裁调用清单与题目细节，固定部分不裁）放在提示的稳定段——运行概况、阶段与耗时、各阶段模型调用的次数 / 耗时 / token / 成本、完整的模型调用清单（带 `call_id`）、交付题与各项核验结论、异常与重试、教师的原话；同一次运行的多轮对话共享这段前缀，缓存命中；②**只读工具**按需取细节：`get_llm_call`（完整提示与回复）、`get_span`、`get_item`（核验证据）、`get_stage_output`（阶段快照）、`find_events`，每轮最多 6 步，结果有长度上限。摘要里的 id 都可直接喂给工具，所以模型既不必猜，也不必把整份记录读进上下文。录制回放的运行在摘要里明确标注"调用耗时是录制值"，避免把回放速度当成真实时延。回答以 SSE 流式返回（文本增量、工具步骤、结束 / 错误）；助手出错只影响这个视图。接口与调试台其他接口一样受令牌保护，助手是只读的，不会改动任何运行或数据。

**会话的改名与删除**：`PATCH /api/sessions/{id}`（标题 1～60 字）与 `DELETE /api/sessions/{id}`。删除在一个事务里级联清掉消息、运行、事件、修订与附件记录，并删除上传目录；会话里还有进行中的运行时返回 409，不允许删。界面上删除要二次确认。
