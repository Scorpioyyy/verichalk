# 项目委托书（Project Brief）

> 本文整理项目发起方对 VeriChalk 提出的目标、约束与工作方式要求，是 [PRD](prd.md)、[指标体系](metrics.md)、[架构](architecture.md) 等文档的**需求来源**。需求有变化时先更新本文，再更新下游文档。文末的"落地对照表"标明每条要求在哪份文档里落实。

## 1. 最终目标

交付一个**前后端全栈**的在线服务：面向小学数学教师的可验证命题 Agent。最终部署到 Zeabur，绑定域名后对外提供服务。

- 同时是一个**工业级**项目：按企业级 Agent 的标准与流程推进——产品需求文档、验收标准、指标体系、评测与 badcase 分析迭代、架构与决策记录——可作为完整的工程作品展示。
- 课程知识来自独立项目 ChalkBase；Agent 在独立仓库，通过其公开接口依赖，不并入知识库。

## 2. 用户与使用方式（已知）

1. **自然语言**：教师用口语化的话让 Agent 出题。
2. **上传图片**：例如现有练习册题目的照片，让 Agent 据此出更多题。

## 3. 核心产品理念

### 3.1 知识库是上下文，不是模板（先验）

知识库按教材原题归纳题型。Agent 应把这些内容当作**"学生学了什么、做过什么"的上下文**，在了解上下文与范围限制之后，出**更具创新性**的题：

- 串联多个知识点的**综合题**（**基于图的检索是这方面最重要的能力**）；
- 适合小学生的**场景化新题**；
- 而不是仅在教材原题上做修改，得到所谓的"新题"。

这应当成为 Agent 的**先验**。**但用户表达了明确意图时，以用户为准。**

### 3.2 用户体验为先

不自娱自乐，时刻从用户角度出发。需要在产品侧认真设计的问题（含但不限于）：

- **数学题排版**很重要：是否使用 LaTeX；是否直接给用户呈现 PDF。
- 用户能**方便地编辑**：直接在页面上改，或用自然语言让 Agent 改。
- 用户能**方便地导出**：PDF、Word、Markdown、LaTeX。
- 耗时较长时，页面是否应**实时显示当前推进到哪里**。
- 出整张卷子这类长任务：是否不要一步到位，而是**先出一些题让用户确认是否符合要求，再进一步完成组卷**。

## 4. 工作方式要求

1. **评测先行。** 从多个角度（产品侧、工程侧）设计一套**结构化的指标体系**，全面监控 Agent 各方面性能，**并分清主次**。指标举例：各阶段延迟、KV cache 命中率等。
2. **架构为先，先把基建搭好。** 先把需要哪些模块、如何耦合定义清楚；Agent 的各个模块、调试、评测等基础设施先行，使后续迭代非常顺畅。**像 ChalkBase 单独收敛一样，基建与能力分开**，不要混在一起。
3. **有主见地收敛。** 先把零散要点收敛成一套完整的闭环体系，再以工程师视角开发与调试；避免后期各种小修小补把项目弄得面目全非；多从全局和用户视角考虑；优先保证可复用的基建与模块，尽可能降低后期迭代成本。
4. **先后端，再前端。**
5. **企业级流程**：产品需求文档、验收标准、badcase 分析与迭代等。

## 5. 调试页面

前端除用户页面外，还需要一个**面向开发者的调试页面**：

- 直观看到一个 query 进来后 Agent **每一步的动向**，便于 debug 与 badcase 分析；
- **全流程可视化**，美观程度要求高；
- 可参考 ChalkBase 知识图谱可视化页面：**图检索时查到哪些节点一目了然**。

## 6. 模型与接口

- 主模型：可用 qwen 系列，也可用 deepseek-v4.1-flash，**看哪个效果好用哪个**（由评测决定）。
- 本地调试阶段可使用国内 DashScope key；**需确认新加坡节点的 DashScope intl key 同样可用**，因为正式部署会选香港或新加坡节点并使用新加坡 key（国内 key 在那里延迟较高）。
- 多模态模型（如 qwen-vl）需**查询最新版本号**，不依赖记忆中的版本。
- 生图 API 暂不作为首版必需（见 PRD §8）；先用结构化规格渲染图形。

## 7. 范围与节奏的取舍

- **先本地 `localhost` 跑通**，暂不考虑 Zeabur 部署；但目录结构与配置要便于之后直接部署。
- **限流与每日额度暂不做。**
- 评测数据：用户将提供**四年级下册练习册照片十余张**作为拍照场景样例；**具体出题需求由开发方自拟**，注重多样性并覆盖边缘情况（但不钻牛角尖）。
- 开发环境使用现有的 conda 环境 `verichalk`。
